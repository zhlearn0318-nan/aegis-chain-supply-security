## 1. 结论先行

当前系统已经证明“能够运行”和“能够形成安装前闭环”，但还缺少三类评委最可能追问的证据：

1. **算法贡献证据**：语义规则、能力一致性、本地模型和动态审计分别贡献了什么，是否只是工具堆叠；
2. **真实可用性证据**：检测率提高后，正常 Skill 是否会因误报而大量进入 REVIEW/BLOCK；
3. **工程稳定性证据**：动态审计在多轮输入、对抗变形、连续运行和 OpenClaw 正式安装流程中是否稳定。

因此，提交前不应再无目标地扩大同一种扫描，而应完成 6 组 P0 实验：

| 顺序 | 编号 | 实验 | 主要回答的问题 | 预计人时 |
| ---: | --- | --- | --- | ---: |
| 1 | E01 | 静态检测组件对照与消融 | 每个静态组件是否真的有效 | 12–16 h |
| 2 | E02 | 静态误报治理与真实生态可用性 | 能否避免“几乎所有 Skill 都不通过” | 8–10 h |
| 3 | E03 | 动态审计 0/1/3 轮消融 | 三轮试运行是否值得额外开销 | 4–6 h |
| 4 | E04 | 动态审计对抗鲁棒性 | 简单混淆或延迟触发能否绕过检测 | 10–14 h |
| 5 | E05 | OpenClaw 端到端稳定性与性能 | 现场连续演示是否可靠、是否足够快 | 8–10 h |
| 6 | E06 | 误报、漏报与典型案例分析 | 系统为什么成功、为什么失败 | 6–8 h |

P0 总计约 **48–64 小时**；另预留 4–6 小时完成结果复核、图表和材料回填，合计 **52–70 小时**。按每天 2–3 小时、提交前 4 周计算，可以落地，但必须按 E01→E06 顺序执行，不能同时扩展生产级权限、集群或全量内核监控。

## 2. 现有证据与本计划的起点

以下结果已经完成，只作为后续实验的冻结对照，不重复包装为新结果：

| 已完成证据 | 当前结果 | 后续用途 |
| --- | --- | --- |
| SkillTrustBench 全量 5,520 条 | Cisco 覆盖率 97.32%，严格宏 F1 0.5090 | 厂商基线与大规模静态背景证据 |
| SkillTrustBench 密封回归 600 条 | 宏 F1 0.4661→0.5629；恶意召回 +8.5 个百分点；正常误报 +3.5 个百分点 | 证明静态增强有效但存在误报权衡 |

当前最重要的事实是：**系统的动态层在受控实验中表现稳定，但静态层仍偏保守；权威文本集上的语义召回仍低，真实官方包最终只有 1/6 自动 ALLOW。** 后续实验必须围绕这个瓶颈设计。

## 3. 统一实验约束

### 3.1 数据隔离与防止“测试集污染”

MaliciousSkillBench 官方 Source-Disjoint test 1,384 条已经运行并完成错误分析，因此它已不是未见测试集。后续必须采用以下协议：

- 官方 `train` 7,513 条：用于轻量模型训练、规则开发和交叉验证；
- 官方 `validation` 835 条：在实验配置、阈值和代码提交冻结后，只运行一次，作为新的来源隔离锁箱集；
- 官方 `test` 1,384 条：允许运行诊断性 v2，但必须明确标注“测试集已被查看后的复测”，不得称为新的独立盲测；
- 既有 SkillTrustBench 600 条回归集：只做兼容性回归，禁止继续调参；
- 真实第三方完整包：用于可用性、动态行为和端到端验证，不与文本基准混算准确率。

若在 E01 锁箱结果出来后继续根据错误修改规则，则修改后的版本不得在同一 835 条结果上声称独立验证；必须另建新锁箱或将结果降级为诊断性证据。

### 3.2 固定比较条件

所有同组对照必须保持以下条件一致：

- 相同样本清单、样本哈希和标签映射；
- 相同 Cisco Scanner 版本、Aegis 代码提交和规则注册表版本；
- 相同 Windows、Docker、Ollama 与本地模型配置；
- 相同超时、并发度、动态轮次和失败闭锁策略；
- 相同 `ALLOW / REVIEW / BLOCK / UNKNOWN` 映射；
- 唯一允许变化的是该实验明确声明的组件或参数。

每个实验必须保存配置、代码提交、样本清单、逐样本结果、汇总指标、运行日志和 SHA-256 校验。失败、超时、UNKNOWN 和负结果不得删除。

### 3.3 统一统计与报告规则

所有有标签的配对实验至少报告：

- 恶意不自动放行召回率；
- 恶意直接 BLOCK 率；
- 良性自动 ALLOW 率；
- 良性直接 BLOCK 率；
- REVIEW 率和 UNKNOWN 率；
- 二分类宏 F1、平衡准确率；
- P50、P95、最大耗时；
- 每来源、每攻击类别和每规则切片结果。

比较两个版本时使用同一样本的配对差值，并报告 10,000 次配对 Bootstrap 95% 置信区间；离散正确/错误变化使用双侧精确 McNemar 检验。样本量很小时只报告计数和置信区间，不以单个百分比宣称普遍有效。

## 4. P0 实验详细设计

### 4.1 E01：静态检测组件对照与消融实验

#### 研究问题

语义规则、声明—实现一致性、轻量文本模型和本地 Qwen 分别带来多少风险检出增量和误报代价？完整系统的提升是否来自某个单一模块，还是来自证据融合？

#### 核心假设

1. 能力一致性和语义上下文能够补足 Cisco 对自然语言操纵与未声明能力的漏检；
2. 轻量文本模型能够扩大语义候选覆盖，而本地 Qwen 适合复核少量冲突样本；
3. 模型证据只升级到 REVIEW、不得单独 BLOCK，可以在提升恶意不放行召回的同时控制良性直接阻断率。

#### 数据集

- 训练与开发：MaliciousSkillBench 官方 `train` 7,513 条；
- 锁箱验证：官方 `validation` 835 条；
- 兼容性检查：冻结的 SkillTrustBench 600 条，只检查旧指标是否显著退化；
- 诊断性复测：已开封的 Source-Disjoint test 1,384 条，仅作新旧版本错误迁移分析。

#### 待比较版本

| 版本 | 启用组件 | 作用 |
| --- | --- | --- |
| S0 | Cisco only | 厂商基线 |
| S1 | Cisco + Aegis 确定性代码/数据流规则 | 自研传统静态增强基线 |
| S2 | S1 + 声明—实现一致性 | 测量能力对齐贡献 |
| S3 | S1 + 自然语言语义规则 | 测量语义规则贡献 |
| S4 | S1 + 一致性 + 语义规则 + 当前 Qwen 路由 | 当前 P0 完整版本 |
| S5 | S4 + TF-IDF/线性分类器证据源 | 测量轻量语义泛化增量 |
| S6 | S5，但关闭 Qwen | 判断 Qwen 是否值得保留 |

除上述递增链外，再对 S5 做“完整系统每次关闭一个模块”的 leave-one-out 消融，避免因组件启用顺序导致错误归因。

#### 轻量模型协议

- 首选 TF-IDF + Logistic Regression 或线性 SVM，CPU 运行；
- 只使用官方 train 拟合，在 train 内进行按来源分组的交叉验证；
- 模型输出风险分数与高贡献词片段，但其证据最多使样本进入 REVIEW；
- 阈值在 train 的交叉验证结果上选择，目标是在控制良性自动放行损失的前提下最大化恶意不放行召回；
- 官方 validation 在阈值、特征和代码提交冻结前不得运行；
- Qwen 只处理轻量模型高风险、规则冲突或语义不确定样本，并记录调用率、耗时与失败率。

#### 主要指标与判定门

以 S4 为当前系统对照，S5/S6 的主要验收门为：

- 恶意不放行召回提高至少 8 个百分点，或 95% 置信区间下界大于 0；
- 良性自动 ALLOW 率下降不超过 5 个百分点；
- 良性直接 BLOCK 率相对 S4 增加不超过 1 个百分点；
- UNKNOWN 率不高于 S4；
- 本地模型失败时保持失败闭锁，不得被当作安全。

若召回提高但良性允许率损失超过门槛，结论记为 `supported_with_tradeoff`；若 Qwen 对锁箱集没有稳定增量或单位收益过低，则保留接口但不作为默认全量路径。

#### 输出物

- 一张 S0–S6 主结果表；
- 一张“恶意召回—良性允许率”Pareto 图；
- 一张 leave-one-out 贡献图；
- 每来源、攻击类别、规则和模型调用切片；
- 锁箱运行合同、逐样本结果和统计检验文件。

#### 预计工时

12–16 小时，包括数据协议、最小模型实现、消融运行、统计和结果复核。

### 4.2 E02：静态误报治理与真实生态可用性实验

#### 研究问题

系统能否区分“文档中讨论危险行为”和“Skill 实际要求执行危险行为”，并减少正常技术文档、开发工具和运维 Skill 的无必要阻断？

#### 数据组成

建立不与 E01 锁箱混用的真实完整包兼容性集，目标不少于 40 个：

- 既有 24 个真实开源生态弱负标签 Skill；
- 既有 6 个 OpenAI/Anthropic 官方原始脚本 Skill；
- 再补充至少 10 个来源、许可证、提交哈希均可固定的公开 Skill；
- 按低权限内容类、开发工具类、运维/网络/安装类分层，不把“发布方可信”直接等同于“代码安全”。

其中只把经过人工功能核对、无明显高风险执行要求的样本称为“低风险正常组”；涉及远程安装、系统管理、凭据或子进程的样本称为“高权限合法组”，其合理决策可能是 REVIEW，不强求全部 ALLOW。

#### 对照设置

- F0：当前规则与策略；
- F1：加入安全禁止语境、示例/测试语境和不可达片段抑制；
- F2：F1 + 条件触发必须与敏感动作或危险汇点位于同一证据窗口；
- F3：F2 + 拟安装入口/实际调用闭包的可达性证据；
- 所有版本保持 HIGH 确定性数据流不得因发布方或动态 ALLOW 自动降级。

重点分析现有误报热点：

- `AEGIS_SEMANTIC_CONDITIONAL_RISK_TRIGGER`；
- `AEGIS_REMOTE_FETCH_PIPE_SHELL`；
- Cisco `PIPELINE_TAINT_FLOW` 与通用 jailbreak 命中；
- 安全教学文本、安装说明、脚手架和生成类 Skill；
- 包内存在未执行入口时，包级风险与当前调用闭包如何分别呈现。

#### 指标与判定门

- 低风险正常组直接 BLOCK 为 0；
- 低风险正常组自动 ALLOW 率不低于 80%；
- 高权限合法组 UNKNOWN 为 0，直接 BLOCK 必须能指向完整高危证据链；
- 与当前版本相比，真实完整包的无必要 REVIEW/BLOCK 至少相对下降 30%；
- 在 MaliciousSkillBench train 交叉验证和 SkillTrustBench 冻结回归中，恶意不放行召回下降不超过 2 个百分点；
- 所有被降噪的 finding 必须保留为 INFO 或解释性证据，不能静默消失。

#### 输出物

- 40 个真实 Skill 的来源、功能、权限面和入选原因清单；
- 误报热点规则的修改前后对照；
- 低风险与高权限合法组的准入分布；
- 至少 3 个“危险词语但安全语境”案例和 3 个“功能合法但应人工复核”案例。

#### 预计工时

8–10 小时。若新增样本下载或许可证核验困难，可先用现有 30 个真实完整包完成首轮，再将扩充样本列为 P1。

### 4.3 E03：动态审计 0 轮、1 轮与 3 轮消融实验

#### 研究问题

三轮“典型—边界—对抗”输入是否比单轮执行发现更多风险？额外收益是否值得增加扫描时间？

#### 数据与方法

- 使用已冻结的 6 个官方原始包与 30 个受控风险孪生；
- 使用同一次三轮运行的逐轮证据做前缀重放，形成三个严格可比版本：
  - D0：只有静态审计，不执行容器；
  - D1：只使用 typical 第一轮证据；
  - D3：使用 typical、edge、adversarial 三轮证据；
- 若现有日志缺少逐轮独立终态，则按同一提交和镜像重新运行，不允许用人工推测补齐。

#### 指标

- 风险孪生不放行召回；
- 预期动态规则召回；
- 静态 ALLOW→动态 REVIEW/BLOCK 数量；
- 静态 REVIEW→动态 BLOCK 数量；
- 首次触发轮次分布；
- 原始官方脚本动态 ALLOW 率；
- 每种方案 P50/P95 耗时和容器调用数。

#### 决策规则

- 若 D3 相比 D1 额外发现至少一种风险类型或召回提高至少 5 个百分点，且 P95 总耗时不超过 D1 的 2.5 倍，则保留三轮为默认；
- 若 D3 没有检测增量，则默认改为一轮，只有第一轮进入 REVIEW 或存在冲突证据时再执行后两轮；
- 若 D3 增加误报或不稳定，则保留负结果并分析触发轮次，不得只汇报最佳轮次。

#### 输出物

- D0/D1/D3 配对结果表；
- 首次触发轮次堆叠图；
- 检测收益—耗时曲线；
- “继续三轮”或“条件升级”的明确工程决策。

#### 预计工时

4–6 小时；优先复用现有逐轮证据，避免不必要的 108 次重复容器调用。

### 4.4 E04：动态审计对抗变形与绕过鲁棒性实验

#### 研究问题

当前 Python/Node/Shell 语言钩子能否检测直接行为的简单变形？攻击者通过编码、间接调用、变量拼接或延迟触发时，系统会不会错误 ALLOW？

#### 安全边界

本实验只运行受控风险孪生，不执行已知恶意第三方 Skill：

- 读取对象仅为容器内诱饵文件，不使用真实凭据；
- 网络保持 `none`，外联只验证尝试事件；
- Skill 和工具目录只读，非 root、丢弃全部 capabilities；
- 固定 CPU、内存、PID 和总超时；
- 每次运行后验证输入树哈希、容器残留和宿主副作用。

#### 样本设计

构造 24 个最小变形样本，Python、Node、Shell 各 8 个，至少覆盖：

1. Base64/十六进制字符串解码后形成命令；
2. 环境变量与字符串分段拼接敏感路径；
3. 间接导入或别名调用子进程 API；
4. 临时文件落地后再执行；
5. 第二或第三轮才触发的延迟行为；
6. 父子进程链式启动；
7. 敏感读取与外联尝试分步发生；
8. 超时、异常或遥测缺失时的失败闭锁。

每个变形必须对应一个未变形对照，且只改变一种绕过因素。不得把多种变化混在一个样本中后声称识别了具体机制。

#### 指标与判定门

- 受控高风险样本非自动放行率：目标 24/24；
- 与预期风险家族一致的证据召回：不低于 90%；
- UNKNOWN/基础设施失败必须保持非放行；
- 原始安全对照动态误报为 0；
- 三轮证明、安全门、清理、输入树不变率均为 100%；
- 宿主真实文件修改、网络成功外联和残留容器均为 0。

任何高风险变形被 ALLOW 都属于有效反例。若无法在提交前修复，应保留案例并把“语言级钩子可被特定方式绕过”写入能力边界。

#### 输出物

- 24 个对抗样本清单与唯一变化说明；
- 按运行时和绕过类型的召回矩阵；
- 至少 2 个成功检测和 1 个失败/边界案例的原始日志；
- 对是否需要 P1 独立系统遥测的决策。

#### 预计工时

10–14 小时。

### 4.5 E05：OpenClaw 端到端稳定性与性能实验

#### 研究问题

用户在真实 OpenClaw Web 控制台上传、扫描、安装、阻断或更新 Skill 时，整个闭环能否连续稳定完成，并满足现场演示等待时间？

#### 场景矩阵

至少建立 12 个端到端场景，覆盖：

- 纯指令、Python、Node、Shell 四种 Skill；
- ALLOW、REVIEW、BLOCK 三种终态；
- ZIP 上传与本地文件夹两种入口；
- 首次安装与同名确认更新；
- Docker 不可用、本地模型超时、扫描器报错等失败闭锁；
- PDF 报告、审计记录、规则版本与页面决策一致性。

正常 12 场景重复 3 轮，共 36 次；另做并发提交 1、3、5 个任务的队列试验。冷启动和热启动必须分开报告。

#### 指标与判定门

- 36/36 场景达到预期终态；
- 不允许安装的样本进入正式 Skill 目录次数为 0；
- 扫描资格哈希与安装时内容不一致时，成功安装次数为 0；
- 审计链、页面、API 与 PDF 的最终决策一致率 100%；
- 容器与临时目录残留为 0；
- 动态完整闭环 P95 用户等待时间低于 60 秒，最大不超过 120 秒；
- 队列重复执行、并发 running>1、永久中间态均为 0；
- 本地模型、Docker 或 Cisco 失败时不得回退为 ALLOW。

性能报告至少给出：静态扫描、模型复核、容器启动、三轮执行、报告生成、OpenClaw 安装六个阶段的 P50/P95/最大耗时，以及峰值 CPU、内存和本地模型调用次数。

#### 输出物

- 12 场景验收矩阵与 36 次逐运行记录；
- 冷/热启动瀑布图；
- P50/P95/最大耗时表；
- 现场演示用的稳定 ALLOW、REVIEW、BLOCK 三件套；
- 一份失败闭锁案例和恢复记录。

#### 预计工时

8–10 小时。

### 4.6 E06：误报、漏报与典型案例分析

#### 研究问题

系统主要在哪些自然语言、能力边界和执行路径上失败？改进后的总体数字是否由少数来源或单一规则驱动？

#### 样本选择

在 E01 锁箱结果完成后，确定性抽取 120 个错误样本：

- 60 个恶意但被 ALLOW 的样本；
- 60 个良性但进入 REVIEW/BLOCK 的样本；
- 按来源、攻击类别、命中规则和文本长度分层；
- 若某类不足 60 个则全量纳入，不使用重复样本补足。

E06 是对锁箱结果的**事后解释**，不能再用这些案例调规则后把同一锁箱结果称为独立验证。

#### 分析量表

每个样本至少标注：

1. 真实意图位于说明、示例、禁止语境还是执行指令；
2. 是否存在声明—实现不一致；
3. 是否涉及敏感数据、外联、子进程、持久化或权限扩大；
4. 失败原因属于规则缺失、上下文范围错误、可达性错误、解析失败、模型判断错误还是标签边界争议；
5. 最合理处置是 ALLOW、REVIEW、BLOCK 还是 UNKNOWN；
6. 是否需要静态规则、轻量模型、本地 Qwen、动态验证或人工复核。

若能获得指导老师或队友协助，对至少 20% 样本做第二人盲标并报告 Cohen's kappa；若没有第二标注者，则明确写为单标注者定性分析，不虚构一致性指标。

#### 指标与完成门

- 至少 90% 错误样本可归入明确原因类别；
- 输出前 5 类误报和前 5 类漏报原因及其占比；
- 每项拟议规则修改至少由 5 个同类案例支持，并同时给出正常反例；
- 选出 6–8 个可在答辩中讲清楚的案例，至少包含成功检出、误报、漏报和 REVIEW 边界各一例；
- 负面结果和标签争议单独列出，不强行判定系统正确。

#### 输出物

- 错误分类表和原因分布图；
- 规则级 precision/false-positive contribution 排名；
- 6–8 个完整案例卡片；
- 下一版规则“新增、收紧、保持或删除”的证据化建议。

#### 预计工时

6–8 小时。

```text
demo_web/artifacts/experiment/<date>-<experiment-id>-v1/
```

其中：

## 9. 最终答辩应形成的证据链

六组 P0 实验完成后，应能够回答以下问题：

| 评委问题 | 对应证据 |
| --- | --- |
| 为什么不直接使用 Cisco？ | E01：Cisco 与各增强组件的配对结果 |
| 是否只是把规则、大模型和 Docker 拼在一起？ | E01/E03：组件消融与轮次消融 |
| 为什么真实 Skill 不会全部被阻断？ | E02：低风险正常组与高权限合法组的可用性结果 |
| 动态审计到底比静态多发现了什么？ | E03：静态遗漏补齐与 REVIEW→BLOCK 增量 |
| 攻击者稍微混淆代码是否就能绕过？ | E04：24 个最小对抗变形及失败边界 |
| 现场演示会不会卡住或留下危险文件？ | E05：36 次端到端、P95 延迟、残留和审计一致性 |
| 系统还会错在哪里？ | E06：误报、漏报和典型失败案例 |

完成后的合理主张应是：

> 系统在权威来源隔离数据上通过对照与消融验证静态增强的独立贡献，并在真实完整 Skill 与受控风险孪生上验证动态审计的增量、鲁棒性和端到端稳定性；同时公开误报、漏报、语言钩子和单机部署边界。

不能主张：

- 对任意未知 Skill 均能准确检测；
- 动态风险孪生等于真实恶意生态样本；
- Docker 等于虚拟机或内核级完全隔离；
- 已开封测试集上的诊断性提升等于新的独立盲测结果；
- 少量官方样本 100% 通过即可证明总体误报率为 0。
