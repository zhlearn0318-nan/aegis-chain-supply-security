# XA-202620 供应链安全模块：评委审查与后续完成清单

> 审查日期：2026-08-21  
> 审查范围：供应链安全模块的代码、演示系统、实验结果、测试证据、PPT 与阶段性报告  
> 目标节点：2026 年 8 月底完成开发，进入最终作品提交材料准备阶段  
> 说明：本文是基于当前证据的模拟评委审查，不代表赛事官方评分。

## 1. 总体结论

当前供应链安全模块已经形成“可运行原型 + 全量基线实验 + 自研静态增强 + 安全动态验证夹具 + Web 演示”的工程成果，不再停留在概念设计阶段。

但是，按最终作品提交和现场答辩标准，当前版本仍不能直接定稿。主要问题不是系统无法运行，而是以下三项核心证据尚未闭环：

1. Aegis 自研增强只在定向开发集上得到验证，尚未运行 600 条封存回归集，泛化效果没有独立证据；
2. 当前能力更接近“扩展组件代码风险扫描”，来源追溯、SBOM、传递依赖和跨组件高危调用链等供应链关键能力仍不完整；
3. PPT、Word 报告和最终提交材料仍停留在早期阶段，与当前 5,520 条全量实验和动态验证成果不一致。

综合判断：项目已经达到“可以演示和继续完善的工程原型”水平，但尚未达到“证据完整、可直接提交的最终参赛作品”水平。

## 4. 已完成且可以作为汇报重点的工作

### 4.1 扫描与策略框架

- 接入 Cisco Skill Scanner、Cisco MCP Scanner 和 pip-audit；
- 建立统一 Finding 数据结构和统一准入策略；
- 支持 `ALLOW / REVIEW / BLOCK / ABSTAIN` 四态结果；
- 扫描异常采用失败闭锁原则，不会把失败任务静默降级为 `ALLOW`；
- 支持 JSON、摘要、策略轨迹和证据导出。

### 4.2 SkillTrustBench 全量基线

已完成 SkillTrustBench v1.0 全量 5,520 条本地离线静态评测，并冻结结果。

| 指标 | 当前结果 |
|---|---:|
| 总样本数 | 5,520 |
| 完成 Cisco 扫描 | 5,372 |
| ABSTAIN | 148 |
| 覆盖率 | 97.32% |
| strict macro F1 | 0.5090 |
| 恶意样本召回率 | 71.11% |
| 恶意样本漏报率 | 28.89% |
| non-normal precision | 86.43% |
| non-normal recall | 77.38% |
| loose F1 | 81.65% |
| 正常样本误报率 | 28.67% |

这些指标能够证明当前冻结配置在公开基准上的表现，但不能证明对现实未知攻击具有相同效果，也不能替代动态验证。

### 4.3 Aegis Static v1 自研增强

当前开发集结果如下：

- 定向漏报补出 21/36；
- T06 持久化风险识别 12/12；
- 20 个正确对照样本决策回退 0；
- 50 个正常开发样本决策升级 0；
- 平均增加约 17 ms/条；
- 不使用 GPU 或大模型。

该开发集是根据旧系统错误挑选得到的，分布不代表真实总体，因此上述结果只能证明规则对已知问题有效，不能写成最终泛化性能提升。

### 4.4 上下文解释增强

- Network Context：16/16 个目标样本获得上下文，36/36 决策保持不变；
- Filesystem Context：8/8 个目标样本获得上下文，28/28 决策保持不变；
- Command Context：6/6 个目标样本获得上下文，26/26 决策保持不变；
- 三类上下文均为 INFO-only，不修改 Cisco 原始 Finding，也不改变最终门禁。

因此，当前可以声明“提高了证据解释能力”，不能声明“已经降低误报率或提高检测准确率”。

### 4.5 安全动态 Fixture v1

- 只运行 3 个自建、哈希锁定的可信 fixture；
- 3/3 fixture 完成，7/7 机制检查通过；
- 策略违规、超时、互联网连接、样本读取/执行、原始 token 泄漏和决策变化均为 0；
- 后端完整测试 142 passed；
- 前端 API 测试 9 passed；
- 前端构建通过。

该模块是动态执行机制与审计链路验证，不是不可信代码沙箱，也没有对第三方 Skill 进行动态恶意检测。

### 4.6 工程原型

当前系统已具备：

- FastAPI 后端接口；
- Web 扫描与结果展示页面；
- 预置样本和自定义上传；
- 扫描历史、决策、策略轨迹和证据展示；
- 管理员动态验证页面；
- JSON 和摘要导出；
- 私有 GitHub 仓库及基本运行文档。

## 6. P0：八月底前必须完成

### 6.1 冻结实现并运行 600 条封存回归集

这是当前最高优先级，必须先于继续增加大量新功能。

执行原则：

1. 先冻结 Aegis Static v1 的代码、规则和策略版本；
2. 一次性运行封存回归集，不提前阅读样本正文；
3. 运行后不得继续根据该回归集调规则；
4. 如结果未达到预期，应缩小或降级宣传结论，而不是反复使用回归集开发。

报告至少包含：

- Cisco 基线与 Cisco+Aegis 的逐案配对比较；
- 正常样本误报率；
- 恶意样本召回率和漏报率；
- strict macro F1；
- T01～T09 分类结果；
- ABSTAIN 数量、类型和原因；
- 新增检出、消除误报和新增误报清单；
- 扫描延迟、吞吐和资源开销；
- 规则版本、代码提交、数据集哈希和运行环境。

验收标准不是“所有指标必须提高”，而是能够诚实、可复算地回答 Aegis 是否具有独立泛化效果，以及代价是什么。

### 6.2 建立最小组件安全护照

至少记录：

- 组件名称、类型和版本；
- 来源 URI、发布者和 commit；
- 上传文件 SHA-256；
- 许可证；
- 直接依赖和传递依赖摘要；
- 简化 SBOM 或 CycloneDX SBOM；
- 扫描器、规则和策略版本；
- 扫描时间、最终决策和证据引用；
- 静态扫描与动态验证关联 ID。

安全护照应进入 API、JSON 导出和前端结果页。该能力能够把系统从普通代码扫描器提升为供应链组件准入系统。

### 6.3 补充最小跨组件高危调用链验证

建议建设 6～12 个可审计的组合样本，至少覆盖：

- 敏感文件读取 → 网络外传；
- 下载 → 解码 → 执行；
- 用户输入 → shell 命令；
- MCP Prompt 诱导 → 高权限 Tool；
- 高危依赖 → 可触达调用点；
- 正常授权调用作为对照。

如果八月底前无法完成，应在最终 PPT 和报告中把该项明确列为后续工作，不能继续放在“已实现架构”中。

### 6.4 扩大 MCP 验证样本

当前 6 个自建样本不足以支持效果结论。建议扩展到 30～50 个分层样本，覆盖：

- Tool、Prompt 和 Resource；
- 正常、恶意及边界样本；
- 命令执行、路径穿越、提示词注入；
- 凭据泄漏和隐蔽外联；
- 同义改写、变量替换和轻量混淆；
- 安全鉴权、日志和管理工具等正常对照。

如果样本不是来自权威公开数据集，应将其称为“经过审计的工程测试集”，而不是“权威基准”。报告需给出混淆矩阵、误报案例和漏报案例。

### 6.5 修复复现和合规问题

- 固定后端 `python-multipart` 等未锁定依赖；
- 将前端 `latest` 依赖改为明确版本；
- 增加项目 LICENSE；
- 增加 THIRD_PARTY_NOTICES 和数据集许可证说明；
- 解决快速启动流程对仓库外 Cisco wheel 的依赖；
- 清理前端和导出结果中的本机绝对路径；
- 在另一台 Windows 电脑上进行全新克隆、安装、启动和扫描验收；
- 创建最终 Git tag 或 GitHub Release，并记录代码提交哈希。

### 6.6 重做最终汇报材料

需要形成以下最终材料：

- 30 页以内技术报告；
- 8～10 页答辩 PPT；
- 5～10 分钟演示视频；
- 一键启动与复现说明；
- 完整指标、逐案结果和结果哈希；
- 攻击样本、审计日志和测试脚本；
- “Cisco 厂商能力—Aegis 自研能力”边界表；
- 已知限制与后续路线。

现有 PPT 和 Word 阶段性报告只可作为历史材料，不能直接用于最终提交。PPT 中来源追溯、SBOM、跨组件检测和完整沙箱仍主要是规划；Word 报告仍围绕 556 条子集展开，已经不能反映当前进度。

## 8. P2：本阶段不建议投入

受剩余时间、个人投入和基础设施条件限制，以下内容不应成为八月底前的主线：

- 支持任意第三方代码的完整 Docker/虚拟机沙箱；
- 云端多租户部署、SSO 和完整 RBAC；
- 复杂外联代理、DNS/TLS 元数据分析；
- 大规模接入更多厂商扫描器；
- 未经消融和成本评估的大模型语义检测。

这些能力可以进入路线图。现阶段继续扩展容易造成核心回归实验和最终材料无法完成。

## 11. 评委可能重点追问的问题

1. Cisco Scanner 已经提供了扫描能力，你们真正自研了什么？
2. Aegis 的 21/36 是否只是针对已知样本调规则？封存集结果是什么？
3. 为什么全量实验的正常样本误报率达到 28.67%，政企用户如何承受复核成本？
4. 148 条 ABSTAIN 分别由什么原因导致，系统如何处理？
5. 动态模块实际执行的是目标 Skill，还是系统内置 fixture？
6. 如何证明组件来源可信、没有在发布后被替换？
7. 是否支持传递依赖、SBOM 和高危依赖可达性分析？
8. Skill、MCP 和依赖之间的高危调用链如何表示和展示？
9. MCP Scanner 的 6 个样本是否足以说明效果？
10. REVIEW 结果由谁处理，是否存在审批、豁免和审计记录？
11. 新电脑克隆仓库后能否离线或按文档完成部署？
12. 为什么结果中会出现本机绝对路径，是否存在隐私泄漏风险？

## 12. 当前唯一优先的下一步

冻结当前静态实现，运行 600 条封存回归集，生成 Cisco 基线与 Cisco+Aegis 的配对结果报告。

在这份结果产生前，不应继续宣传 Aegis 已经提升了未知样本检测效果，也不应优先开发完整动态沙箱或大模型语义增强。
