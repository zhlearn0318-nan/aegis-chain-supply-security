# M14 真实第三方 Skill 动态审计结果与综合准入差距

## 结论

本轮正式实验通过预先冻结的全部阈值。系统对 30 个受控风险孪生的对应动态规则召回率为 100%，风险非放行率为 100%；6 个真实官方原始脚本在动态层全部为 ALLOW，说明容器试运行本身没有造成“几乎所有 Skill 都不通过”。

实验同时暴露出静态层仍偏保守：在不允许动态结果降低静态决策的现行融合策略下，6 个原始 Skill 的最终综合结果为 1 ALLOW、4 REVIEW、1 BLOCK。这个问题不能通过宣称“动态 6/6 ALLOW”来回避。

## 实验事实

- 来源：OpenAI 官方 Skills 5 个原型、Anthropic 官方 Skills 1 个原型；
- 许可证：所选原型均为 Apache-2.0；
- 样本：6 个原始包 + 30 个受控风险孪生；
- 实际执行：36 包 × 3 轮 = 108 次容器脚本调用；
- 已知恶意第三方 Skill：0 个被执行；
- 风险类型：诱饵访问、Shell 启动、敏感路径、外网尝试、对抗轮超时；
- 三轮证明、安全门、容器清理、样本树不变率：均为 100%；
- 单包耗时：中位 5.002 秒，均值 4.387 秒，最大 10.290 秒。

## 动态审计带来的增量

30 个风险孪生在静态层已有 26 个进入 REVIEW/BLOCK，静态非放行召回率为 86.7%。动态层补齐了 4 个静态 ALLOW 漏洞，使综合非放行达到 30/30；同时把 14 个静态 REVIEW 进一步升级为 BLOCK。合计有 18 个样本因动态证据获得更严格决策。

因此，动态审计的主要贡献不是替代静态规则，而是：

1. 观察只有运行时条件满足后才出现的行为；
2. 为静态候选提供可复核运行证据；
3. 将部分不确定 REVIEW 转化为可解释 BLOCK；
4. 对静态 ALLOW 的运行时遗漏形成最后一道安装前安全门。

## 真实原始 Skill 的综合结果

| Skill | 静态 | 动态 | 综合 |
|---|---|---|---|
| OpenAI `jupyter-notebook` | REVIEW | ALLOW | REVIEW |
| OpenAI `plugin-creator` | REVIEW | ALLOW | REVIEW |
| OpenAI `security-ownership-map` | BLOCK | ALLOW | BLOCK |
| OpenAI `chatgpt-apps` | REVIEW | ALLOW | REVIEW |
| OpenAI `openai-docs` | REVIEW | ALLOW | REVIEW |
| Anthropic `algorithmic-art` | ALLOW | ALLOW | ALLOW |

静态 REVIEW/BLOCK 的主要原因包括：

- Notebook 资产尚无专用解析器，被视为未覆盖格式；
- 通用语义条件触发规则对正常脚手架和生成类 Skill 仍偏敏感；
- 包级扫描会检查本次未执行的其他入口，例如 `security-ownership-map` 包内的动态命令执行入口；
- Cisco 对本地文件与网络能力产生候选发现，现行策略保留人工复核。

## 下一步改进方向（本轮不改变决策策略）

1. 增加“拟安装入口 / 实际调用闭包”证据，使包级风险和本次执行路径同时呈现；
2. 为 `.ipynb` 等常见 Skill 资产建立只读结构解析，减少“未覆盖格式”型 REVIEW；
3. 将通用条件触发语义规则与真实数据流、危险汇点或隐匿意图绑定，降低正常脚手架误报；
4. 增加可信发布方、提交哈希、许可证和依赖锁定证据，但这些证据只能降低人工复核成本，不能单独覆盖 HIGH 行为；
5. 保持当前单调融合：在静态 HIGH 尚未被准确限定前，动态 ALLOW 不自动降级静态 BLOCK。

## 汇报时的准确表述

可以说：

> 我们使用 6 个 OpenAI/Anthropic 官方真实脚本及其 30 个受控风险孪生，在断网、只读、非 root 的 Docker 沙箱中完成 108 次三轮脚本调用。动态规则对五类风险均达到 6/6 命中，补齐 4 个静态遗漏，并将 14 个静态复核升级为阻断；6 个原始脚本在动态层均无误伤。

不能说：

> 6 个官方 Skill 最终全部通过。

因为现行静态与动态单调融合后，最终只有 1 个 ALLOW，另有 4 个 REVIEW 和 1 个 BLOCK。这个差距已经被记录为下一阶段静态证据范围和规则精度改进任务。
